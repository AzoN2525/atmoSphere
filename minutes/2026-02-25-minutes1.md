### **Discussões e Decisões**:

#### 1. **Ponto 1: Arquitetura da solução**
- **Discussão**: Foi discutida a adoção de uma arquitetura por camadas. A proposta técnica inclui PostgreSQL como base de dados com modelo relacional, React + Vite no frontend, Spring Boot no backend, RabbitMQ como message broker e um setup em Docker multi-container.
- **Decisão**: Fica definida, nesta fase, uma arquitetura por camadas com a stack tecnológica discutida.

#### 2. **Ponto 2: Mobile app**
- **Discussão**: Foi levantada a questão de, no futuro, poder existir uma aplicação mobile. A equipa reconheceu a importância do tema, mas considerou que ainda existem dúvidas relativamente à necessidade real e à melhor estratégia a seguir (mobile app dedicada ou solução web-based).
- **Decisão**: Este ponto fica por definir. A equipa irá esclarecer dúvidas com o professor antes de fechar a decisão.

#### 3. **Ponto 3: Personas, user stories e backlog**
- **Discussão**: Foi confirmado que o projeto conta atualmente com 12 user stories. Houve discussão sobre a ambiguidade das personas 1 e 2, sendo considerada a hipótese de criar uma nova persona mais específica. Foram também revistas as user stories individualmente.
  
  Em particular:
  - **US1 - Real-Time Environmental Map View**: discussão sobre a melhor forma de representar os dados, incluindo mapas 2D/3D. Foi referida a possibilidade de usar CesiumJS para mapa 3D, mas levantou-se a dúvida se uma API com mapa 3D poderá ser demasiado pesada. Também foi referido Mapbox GL JS como alternativa, apesar de ser potencialmente mais difícil de trabalhar, mas com uma aparência mais clean.
  - **US5 - Environmental Threshold Alert System**: foi discutida a possibilidade de implementar um modelo publish/subscribe para notificações apenas aos utilizadores subscritos, por email, SMS ou outros canais.
  - **US6 - Hourly and Monthly Data Aggregation**: foi identificada ambiguidade na user story, necessitando de esclarecimento.
  - **US9 - Rank Areas by Environmental Performance**: foi proposta uma página com scoreboard das cidades.
  - **US10 - Export Environmental Reports**: ficou em aberto o formato de exportação dos ficheiros.
  - **US12 - Family-Friendly Environmental Zone Assessment**: foi discutida a criação de uma página com sugestão dos melhores locais com base nos melhores índices.
- **Decisão**: Mantêm-se, para já, as 12 user stories. A ambiguidade das personas 1 e 2 e de algumas user stories deverá ser confirmada com o professor.

#### 4. **Ponto 4: Estrutura do repositório**
- **Discussão**: Foi revista a estrutura do repositório de acordo com o guião. Houve também discussão sobre a forma de organizar releases e sobre a importância de trabalhar com GitHub Projects e Git Flow.
- **Decisão**: A estrutura do repositório foi ajustada e confirmada segundo o guião. A equipa continuará a consolidar o processo de trabalho com Git Flow e GitHub Projects.

#### 5. **Ponto 5: Documentação da API**
- **Discussão**: Foi considerada a utilização do framework OpenAPI/Swagger para criar a documentação da API.
- **Decisão**: A equipa irá adotar OpenAPI/Swagger como abordagem de referência para a documentação da API.
